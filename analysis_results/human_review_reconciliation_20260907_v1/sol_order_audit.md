# 50 图点序复顺序只读审查

日期：2026-09-07  
范围：只读核查 Label Studio 原始导出、历史 3D 显示、HD 默认邻接和 12 条独立重排建议。未进行新的视觉判断，未修改预览、问卷或原数据。

## 结论

用户提出的核心质疑成立：HD 流程把 Label Studio `result` 中关键点的**序列化列表顺序**直接解释为“每相邻两点构成一组，组间依次构成相邻墙角”；历史 Label Studio 3D 查看器却会先按 x 坐标排序，再在 5% 图宽阈值内按 x 距离就近配对。两条路径使用的不是同一种点对和墙邻接语义。

因此，HD 报告的 `invalid_original_order_polygon` 只说明“按导出数组相邻项构造的多边形自交”，不能单独证明工人的原始标注或工人实际看到的历史预览自交。反过来，历史查看器或建议能生成网格，也不能证明该网格就是作者本意。

12 条已生成建议本身均没有引入地面自交：建议生成函数在落盘前对 `preview_points` 调用 `audit.footprint(proposed)`，不通过就不会成为建议。12 条均为 `computable`。但是这些建议的索引是**原始导出点 ID**；若把它们当作历史查看器已经排序后的“组索引”再应用，会发生二次重排并可能重新产生自交。

## 代码证据

1. `tools/thesis_main/analysis/upgrade_uncertainty_review_hd.py:14-18`
   - `paired_payload()` 调用 `audit.roles(points)`。
   - 返回的 `ids` 按步长 2 写成 `raw:{ids[i]}/{ids[i+1]}`，因此默认把导出列表的相邻项解释成上下点对。

2. `analysis_results/uncertainty_handoff_received_20260907_v1/original_package/review_code/audit.py:20-26`
   - `roles()` 使用 `a.reshape(-1,2,2)` 和 `np.arange(...).reshape(-1,2)`。
   - 它只允许交换一组内部的 top/bottom 角色，不重新寻找点对，也不恢复历史查看器的 x 排序。

3. 同一文件 `audit.py:40-43`
   - `footprint()` 按上述点对顺序直接构造 `Polygon`；无效时报告 `invalid_original_order_polygon`。

4. `tools/label_studio/config_history/uncertainty_meta_v1_prechange_20260824/zh/userscript/ls_userscript_annotator.js:2691-2718`
   - 历史 userscript 先执行 `points.sort((a, b) => a.x - b.x)`。
   - 随后在 `W * 0.05` 阈值内寻找 x 距离最近的未使用点，构造 `pairedDefault`。
   - 当前 `tools/label_studio/official/ls_userscript_annotator.js:2412-2442` 仍保留同样的默认预处理。

5. `tools/thesis_main/analysis/prepare_uncertainty_visual_review.py:65-102`
   - `preview_order()` 首先尝试沿用 HD 推断的相邻点对，再按底点 x/方位角排序。
   - 第 101 行用 `audit.footprint(proposed)` 检查建议结果，所以“能成为建议”只证明该特定推断可计算，不证明作者邻接。

6. `tools/thesis_main/analysis/audit_uncertainty_review_order.py:67-82,93`
   - 人类记录逐点核对为原始导出坐标。
   - 已核查的人类记录没有 `relation` 可证明墙邻接。
   - 文件明确记录 `proposal_applied_to_hd_or_studio=False` 和 `author_intended_order_verified=0`。

## 重点数值反例

### V03 / W8

- 原始导出点对按相邻项读取为：`(0,1),(2,3),(4,5),(6,7)`。
- 四组 x 坐标依次约为：`622.803, 902.747, 351.908, 167.219`。
- HD 按此组序构造地面，结果为 `invalid_original_order_polygon`。
- 历史查看器按 x 排序后的点序是：`[6,7,4,5,0,1,2,3]`。
- 这与独立建议完全一致；该顺序地面可计算，面积约 `3.519039`。

这不是“建议发现并修复了工人的错误”，而是建议重新产生了历史查看器早已使用的显示顺序。

若把建议对应的组排列 `[3,2,0,1]` 再作用于历史查看器已经排序后的四组，得到的原点顺序为 `[2,3,0,1,6,7,4,5]`，再次触发 `invalid_original_order_polygon`。这证明原始点 ID 映射不能直接作为已排序组的排列输入。

### V06 / W10 与 W13

两个版本的八个坐标完全一致：

- 点 0、1、2、3 的 y 分别约为 `256.705, 257.255, 317.156, 316.607`，均位于下半球。
- 点 4、5 的 y 约为 `195.924, 197.107`，位于上半球。
- 点 6、7 的 y 约为 `355.098, 353.915`，位于下半球。

也就是 2 个上点、6 个下点，无法组成四个合法的上下端点组。HD 的 `adjacent_pair_same_hemisphere` 不是单纯改变组序可以修复的问题。

历史查看器仍会按 x 距离贪心组成 `(2,0),(3,1),(7,4),(6,5)`；前两组都是下点配下点。旧页面即使能画出线框，也不能据此宣称标注拓扑有效。现有建议文件对两条均保持 `unresolved`：原因为 `unequal_endpoint_roles`，没有生成重排方案。

### V10 / W15

- 原始相邻组为 `(0,1),(2,3),(4,5),(6,7)`。
- `(2,3)` 的 y 约为 `242.662, 230.615`，两个都是上点。
- `(6,7)` 的 y 约为 `306.339, 297.734`，两个都是下点。
- 因此 HD 报 `adjacent_pair_same_hemisphere`。
- 历史查看器按 x 就近配为 `(1,0),(2,7),(3,6),(5,4)`；角色规范化后等价于 `(0,1),(2,7),(3,6),(4,5)`，该地面可计算。

该例直接说明 HD 红线来自“相邻导出项就是点对”的假设，不足以证明工人历史预览有自交。现有建议文件仍保持 `unresolved`，原因为 `nonunique_vertical_pairing`，没有生成重排方案。

## 建议的解释边界

1. 应把“导出列表顺序”“上下点配对”“墙环邻接”“历史显示顺序”作为四个独立字段或概念，不再互相代替。
2. 在不存在显式 `relation` 或其他协议证据时，不能把导出数组邻接命名为“作者原始墙顺序”；最多称为“序列化相邻假设”。
3. 12 条建议可作为可视化候选，但不能作为修复真值；尤其不能以能生成非自交网格作为正确性证明。
4. 若将建议用于官方查看器，必须先把原始点 ID 映射转换到 `pairedDefault` 的组索引空间，不能直接二次应用。
