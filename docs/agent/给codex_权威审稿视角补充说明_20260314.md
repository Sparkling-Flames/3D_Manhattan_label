# 给 Codex 的补充说明：基于实际提纲与实验集设定的权威审稿视角修订版（2026-03-14）

## 一、这份修订的核心结论

这次根据你已经上传的两份关键文件——`论文提纲v2__15_.pdf` 与 `实验集设定与用途.md`——可以把之前的研究判断进一步收紧为一句话：

**HOHONET 当前的方法学逻辑，不是“embedding 聚类驱动的 scene routing”，而是“PreScreen 的专家锚点负责切断循环论证并建立全局基线，Calibration 才正式估计全局与场景特异可靠度，difficulty/model_issue 的共识标签充当 scene proxy，embedding 只作为 calibration-only 的 OOD / 分布风险参考，不直接定义 scene，也不直接充当路由主裁决器”。**

这比之前“可能用 embedding 聚类定义 scene”更准确，也更符合当前提纲文本。

## 二、建议代入的权威审稿人视角：Pietro Perona

如果要在这个领域里找一位最贴近你当前问题结构的权威人物来代入审稿视角，我建议优先采用 **Pietro Perona** 这一条学术谱系，再辅以 **Jacob Whitehill（GLAD）**、**Ece Kamar（task-dependent bias / active expert correction）**、**Yunus Emre Kara（active crowd-labeling / dominance suppression）** 与 **Shixia Liu（interactive expert validation）** 作为补充参照。

原因不是“他最有名”这么简单，而是因为你的问题正好跨了这几件事：

1. worker 的全局能力与任务异质性不能混为一谈；
2. task / scene 本身也有结构；
3. 机器初始化会改变人的行为；
4. 派单不是静态分类，而是带探索-利用约束的顺序决策；
5. 需要可解释、可审计，而不是黑盒路由。

Perona 及其合作者的两条代表性工作恰好卡在这条主线上：

- **The Multidimensional Wisdom of Crowds**：把 annotator competence / expertise / bias 与 image/task 的差异一起建模；
- **Lean Crowdsourcing**：把 worker skill、image difficulty、model prediction 放到同一个顺序式风险估计框架中。

因此，若采用“Perona 式审稿口径”，你现在的设计总体是合理的，但必须把“层级分工”写得比现在更清楚。

## 三、结合提纲与实验集设定，对你原问题的精确回答

### 1. PreScreen 的人工专家锚点，到底在估计什么？

根据 `实验集设定与用途.md`，PreScreen_manual 的 20–22 个 manual anchors 属于独立真值锚点；它们的职责是：

- 估计初始可靠度锚点 `r_u^(0)`；
- 锁定 admission；
- 锁定 `w_max`；
- 识别明显不合格或工程不可用的工人。

文件同时明确写了：PreScreen 的核心产物是 `admission`、`r_u^(0)`、盲信初始化风险的早期证据，以及加权共识的独立权重锚点与 `w_max`，**而不是**最终的 `r_u`、`r_u^(s)` 或完整 routing 画像。

因此，结论应当固定为：

**PreScreen 的专家锚点估计的是“全局基础可靠性 + 准入基线”，不是场景特异可靠性。**

你原先用专家精标来避免循环论证的思路是对的；真正的问题不在于“这个想法是否合理”，而在于后续写作必须清楚声明：

- 它是 independent expert-reference anchor；
- 它服务于 `r_u^(0)` 与 `w_max`；
- 它不应被误写成 scene-specific reliability 的主来源。

---

### 2. Calibration 才是正式估计 `r_u` 与 `r_u^(s)` 的阶段

根据 `实验集设定与用途.md`，Calibration_manual 的职责被定义为：

- 估计全局可靠度 `r_u`；
- 估计场景特异可靠度 `r_u^(s)`；
- 估计其置信区间与 `LCB(r_u)`；
- 识别条件性脆弱风险 `C_u`；
- 冻结核心场景集合和 scene-routing 启用规则；
- 构建 `d_t` 的 calibration-only embedding 参考库，并据此冻结 `tau_d` 与 `I_t^{OOD}`。

这意味着你的体系里有一个非常清楚的层级分工：

- **PreScreen_manual**：独立 expert anchors，用于 `r_u^(0)` 与 `w_max`；
- **Calibration_manual**：正式 worker statistics，用于 `r_u`、`r_u^(s)`、LCB 与 scene-routing 启用规则。

这正是一个严谨审稿人希望看到的分工。

---

### 3. scene 不是 embedding 聚类出来的；scene 的主定义来自 difficulty + model_issue 共识

这一点现在已经可以非常明确地写死。

在 `论文提纲v2__15_.pdf` 中，RQ3 直接写明：

- **场景定义：以 difficulty 与 model_issue 的共识标签作为场景代理；**
- 全部标签进入审计集合，并报告频率、共现与反例分布；
- 路由只在不超过 `Score,max = 4` 个核心场景上启用，并披露启用率与退化率。

提纲对低一致性 tag 的处理也写得很具体：

- 低频 tag 进入审计，不进入细粒度路由；
- 一致性不足的 tag 应与相近 tag 合并成粗粒度场景；
- 即便继续报告，也必须带低一致性警告，并在路由中使用其 LCB 而非点估计。

因此，当前正确表述不是“scene 来自 embedding 聚类”，而是：

**scene 的论文主口径来自 difficulty / model_issue 的共识标签，经频率与一致性约束后冻结成 `core_scene`；embedding 不是 scene 定义器。**

---

### 4. embedding 的位置：不是 scene 定义器，而是 calibration-only 的 OOD / 风险参考库

`实验集设定与用途.md` 已明确：

- Calibration 要“构建 `d_t` 的 calibration-only embedding 参考库，并据此冻结 `tau_d` 与 `I_t^{OOD}`”。

这句话非常关键。它说明 embedding 在你体系里的职责是：

- 做 `d_t` 风险代理；
- 做 OOD 触发；
- 给 `I_t^{OOD}` 提供 calibration-only 参考；
- 服务于 Validation / routing 的风险分层；

而不是：

- 直接把任务聚成 scene；
- 直接作为 worker×scene 的主契约；
- 直接决定工人画像的顶层分组。

所以你之前那个疑问，现在可以得到明确答案：

**后面的派单不是“按 embedding cluster 派单”；embedding 只是一个 pre-label risk / OOD 代理，真正路由主口径依赖于风险触发 + 全局 / 场景特异可靠度 + 启用/退化规则。**

---

### 5. difficulty 标签到底有没有用于场景分类？

有，而且很关键；但用法比“拿 difficulty 训练一个场景分类器”更克制。

按提纲，difficulty 与 model_issue 的共识标签共同充当 `scene proxy`。这意味着 difficulty 的作用主要在：

- 构成 `core_scene` 候选；
- 支撑 `Worker × Scene` 和分层报告表；
- 支撑路由启用/退化审计；
- 支撑反例分布与共现分析。

所以不能再说“difficulty 好像没用到”，更准确的说法应该是：

**difficulty 被用于定义 scene layer，而不是用于定义 worker portrait 的最顶层主轴。**

---

### 6. 为什么你会感觉“工人画像没用到这些东西”？

因为提纲里的 worker portrait 顶层，并不是按 difficulty/model_issue 直接分人，而是按更稳的 worker statistics 分人。

当前提纲与相关审计口径显示，worker portrait 更接近以下几层：

- 全局可靠度层：`r_u` 或 `LCB(r_u)`；
- 风险层：例如 blind-trust 风险 `T_u`、条件性脆弱风险 `C_u`；
- 后续可能的 worker group / quadrant portrait；
- scene layer 则通过 `r_u^(s)` 与 Worker × Scene 表来进入。

也就是说，你不是“没用 scene 信息”，而是：

- **worker portrait 顶层**：更偏全局能力 / 风险层；
- **scene layer**：difficulty + model_issue 进入 `r_u^(s)`、Worker × Scene、route attribution；
- **routing layer**：再把二者结合起来。

这在方法上可以成立，但写作上必须更清楚。不然审稿人会问：

> 既然 difficulty / model_issue 是 scene proxy，为什么它们在工人画像与归因链里的存在感这么弱？

这是你后面最需要补强的表达问题之一。

## 四、以 Perona / Whitehill / Kamar / Kara / Liu 的综合权威视角，对当前设计的审稿式评价

### 4.1 会被认可的部分

#### （1）用独立 expert anchors 打破循环论证
这部分逻辑是对的，而且是你方案最重要的优点之一。

提纲 2.3.2 已经明确要求：权重 `w_u` 的来源必须独立于当前任务的标签与共识计算，优先来自 PreScreen 的专家参考标准得到的初始可靠度 `r_u^(0)`，其次才是 Calibration 的 leave-one-task-out 估计。

这与 learning-from-crowds 里“不要用同一批 crowd labels 既定义可靠度、又评价可靠度”的基本审稿要求一致。

#### （2）把 scene proxy 留给可解释的 meta-label，而不是直接交给 embedding cluster
这比很多“看起来更聪明”的设计更稳。

原因很简单：一旦 scene 主口径由 embedding cluster 定义，你就必须回答 cluster 稳定性、语义解释、seed 敏感性、聚类超参数、与错误模式的一致性等一串问题。现在你把 scene 留在 `difficulty + model_issue` 共识层，把 embedding 限定在 OOD / 风险代理层，审稿压力会小很多。

#### （3）把 Calibration 和 Routing 放在 PreScreen 之后，而不是提前宣称场景路由已成立
这点也是正确的。

提纲和实验集设定都强调：Pilot 锁协议骨架；PreScreen 锁 admission 与加权相关阈值；Calibration 第一轮后，才冻结依赖场景覆盖的 scene-routing 参数与 OOD 触发参数。这个阶段化锁定，符合严谨研究设计。

---

### 4.2 会被严厉质疑的部分

#### （1）当前提纲的“概念层”比“产物层”更完整
也就是说，方法说得清楚，但证据链还没完全接上。

从 `提纲一致性审计_20260313.md` 可见，当前最明确的硬问题有四类：

- Stage 1 配额未对齐；
- formal thesis input 当前 blocked；
- RQ1 `active_time` 仍混有 fallback；
- 第 4 章正文级证据链尚未形成。

这意味着：你的理论分工现在基本对，但正文产物还不足以完全承接这些主张。

#### （2）worker portrait、scene layer、routing layer 的关系，仍然没有被写得足够“让审稿人一眼懂”
你的内在逻辑其实已经存在了：

- portrait 看全局 `r_u` / 风险层；
- scene 看 `r_u^(s)`；
- routing 用 scene + risk + reliability；

但当前表达还没有把这三层显式画成一个干净的因果/信息流关系图。审稿人很容易误会成：

- 你收了 difficulty，但没真用；
- 你说有 scene-specific reliability，但画像里看不见；
- 你说 routing 用了 scene，但 scene 又像是后补的。

这不是设计错误，而是**写作与产物组织错误**。

#### （3）参考文献当前写法有明显问题，必须尽快修
这是一个非常具体、而且必须马上改的问题。

你上传的实际论文中：

- `Actively Estimating Crowd Annotation Consensus` 的真实作者是 **Yunus Emre Kara, Gaye Genç, Oya Aran, Lale Akarun**；
- `An Interactive Method to Improve Crowdsourced Annotations` 的真实作者是 **Shixia Liu, Changjian Chen, Yafeng Lu, Fangxin Ouyang, Bin Wang**。

但你当前提纲 PDF 第 30 页参考文献里对应条目写成了类似：

- `E. Kara and J. Smith ...`
- `W. Liu and M. Chen ...`

这明显不是准确引文格式。这个问题不属于“后面再润色”，而是会直接损害可信度的硬伤。  
**必须让 Codex 先把这两条文献替换成真实题目、真实作者、真实 venue。**

### 5.2 我认为仍需要正面修订的地方

#### （1）在 2.6、2.7、2.8 附近，建议增加一段“层级职责声明”
建议明确写成类似：

- PreScreen_manual anchors → `r_u^(0)` / admission / `w_max`

- Calibration_manual → `r_u`, `r_u^(s)`, `C_u`, `LCB(r_u)`

现在这些信息分散在不同小节里，但缺一段“一图读懂”的总声明。

#### （2）工人画像要明确分成“portrait layer”和“scene layer”
建议不要再把所有内容都压进一个 worker profile。

更稳的写法是：

- **Worker Portrait（顶层画像）**：`r_u`、`LCB(r_u)`、`T_u`、`C_u`、worker group
- **Worker × Scene（条件画像）**：`r_u^(s)`、场景覆盖、启用/退化警告

这样审稿人就不会问“difficulty / model_issue 去哪了”。

#### （3）第 4 章要更明确地把三层证据链串起来
你现在第 4 章写了 T/I/M、分层表、反例库、过程证据与归因链，这是对的；但建议在 4.4 显式写出：

- portrait 提供人层基线；
- Worker × Scene 提供条件性能力；
- difficulty/model_issue 共现与反例库提供任务层解释；
- route attribution 再把“为什么这样派”闭环起来。
