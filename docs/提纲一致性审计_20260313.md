# 提纲一致性审计（2026-03-13）

## 审计目的

把中文提纲 `docs/overleaf_project/main.tex` 及其分章要求，逐项对到当前仓库的真实输入、输出、约束与代码边界，回答三个问题：

1. 当前仓库与提纲在哪些地方方向一致；
2. 哪些地方只是“部分对齐”，还不能当正文证据；
3. 哪些地方已经构成硬冲突或 thesis-facing blocked 状态。

---

## 一页结论

- 研究设计主线与提纲一致：当前仓库仍然围绕 `Pilot -> PreScreen -> Calibration -> Main(Test + Validation)` 组织，没有出现方法论层面的方向冲突。
- 当前最明确的硬不满足有 4 类：
  - Stage 1 配额与提纲不一致：`PreScreen_manual anchor` 仍是 12，不是 20--22；`PreScreen_semi` 仍是 30，不是约 18。
  - formal thesis input 当前应视为 `blocked`：现有 `export_label/` 导出全部被排除在 formal estimand 之外，且 runtime-to-plan join 仍有 `unmatched/ambiguous`。
  - RQ1 的 `active_time` 当前仍是 `direct active log + lead_time fallback` 的混合量，不是提纲意义上已经可直接比较的统一主终点。
  - 第 4 章有原型产物，但还没有形成 thesis-eligible 的主证据链。
- 当前最接近“附录承诺已部分兑现”的是 C 线：算子库、materialization 与 reject family 已经可核查；但生命周期字段、family 覆盖与 thesis-facing completeness 还未闭环。

## 1. active_time 专项核查

### 1.1 当前 registry 的真实口径

数据源：

- `analysis_results/registry_20260308/annotation_registry_v1.csv`
- `analysis_results/registry_20260308/active_time_registry_v1.csv`
- `analysis_results/pooled_qa/registry_20260308/summary.json`

当前 `active_time_source` / `active_time_match_status` 计数如下：

| 范围 | log + task+annotator | fallback_no_direct_log | fallback_log_present_but_no_direct_match |
| --- | ---: | ---: | ---: |
| 全部 annotation rows | 56 | 128 | 5 |
| 已 matched 到 registry 的 rows | 39 | 70 | 5 |

解释：

- `active_time_source=log` 才是 direct active log 命中。
- `lead_time_fallback` 只是回退到 Label Studio `lead_time`，不是提纲里定义的 active interaction time。
- `analysis_results/pooled_qa/registry_20260308/summary.json` 已经明确把这一点写成注释，不允许混讲。

### 1.2 按 dataset_group 看 direct-log 覆盖

已 matched rows 中，direct-log 子集分布如下：

| dataset_group | condition | direct-log rows |
| --- | --- | ---: |
| `Gold_manual` | manual | 2 |
| `PreScreen_manual` | manual | 4 |
| `PreScreen_semi` | semi | 7 |
| `Calibration_semi` | semi | 5 |
| `SemiAuto_Test` | semi | 13 |
| `Validation_semi` | semi | 8 |

关键事实：

- 当前 matched registry 中没有 `Manual_Test` 的 direct-log rows。
- 这意味着 RQ1 若坚持“主终点 = 提纲定义的 active interaction time”，当前仓库并不具备直接跑 `Manual_Test vs SemiAuto_Test` 主比较的完整 direct-log 输入。

### 1.3 对 RQ1 的协议判断

结论：

- 当前 `active_time` 不能直接被表述成“已经满足提纲主终点定义”的主分析输入。
- 更稳妥的写法应是：
  - `direct-log` 子集只能先作为敏感性分析或计时实现核查；
  - `lead_time_fallback` 若继续进入正文，必须被明确声明为与主定义不同的 fallback estimand，而不是静默混入。

补充缺口：

- 提纲第 4.1 节还要求固定披露 `task_id/annotator_id/project_id unknown`、`script_version` 缺失、多 session 占比等 active-time 数据质量项。
- 当前 registry 虽有 `active_time_session_count` / `active_time_event_count` 字段基础，但还没有形成固定审计表；`docs/约束审查意见_20260306.md` 也已指出这一点尚未完全对齐。

### 4.3 unmatched / ambiguous 风险

- task 级 join 有 `33 unmatched + 32 ambiguous`

- 当前 thesis path 不能从 `export_label/ + runtime export join` 直接启动；

### 5.3 当前 reject 的真实边界

当前 2 个 reject 都集中在同一窄 family：

- `operator_id=underextend`
- `lambda_level=medium`
- `source_corner_count=4`
- `failure_code=transform_degenerate`

对应文件：

- `analysis_results/c_manifests_20260311/trap_manifest_materialized_v2.csv`
- `analysis_results/c_manifests_20260311/synthetic_trap_bank_v1.json`

代码原因：

- `tools/perturbation_operators.py` 中 `UnderExtendOperator` 对 `medium` 固定 `removal_count=2`；
- 对 4-corner 输入，第一次删点后只剩 3 个 corner；
- 第二次删点前触发 `transform_degenerate` reject。

所以当前更准确的结论是：

- 不是整个 `underextend` family 都坏了；
- 而是 `4-corner + medium underextend` 这条子边界在当前实现下必然 reject。
